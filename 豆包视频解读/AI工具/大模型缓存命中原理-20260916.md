# 什么是缓存命中，为什么大模型回答会突然变快？

> **视频主张**：同一段提示词，第一次问很慢，第二次问突然秒回——模型没变聪明，是它把上次算过的那段**中间结果**直接拿来复用了。
>
> **核心矛盾**：很多人以为缓存的是"答案"，所以看到回答内容不一样就困惑"明明没命中怎么还变快了"。**缓存的是输入文本的模型计算状态，不是输出文本。**

**一句话结论**：大模型回答变快，是因为这次请求的**前缀（从第 0 个 token 开始的那段）**之前算过，直接跳过最耗算力的 **Prefill（预填充）**阶段，只算末尾新增的内容。

---

## 一、先搞懂大模型处理文字的两个阶段

| 阶段 | 干什么 | 特点 |
|:--|:--|:--|
| **Prefill（预填充）** | 读取全部输入 Prompt，计算每个 token 的 K/V 向量 | **最耗 GPU、最贵、最慢** |
| **Decode（生成）** | 逐字输出回答 | 每步只算一个新 token |

**关键动作**：缓存机制把 Prefill 算出的 **K/V 向量**存起来。下次只要开头完全一样，直接读缓存跳过重复 Prefill，只计算末尾新增的文字。

> 📌 四个向量名词一次性说明白（Transformer 注意力层）：每个 token 会算出 **Q（Query，我要关联什么）**、**K（Key，我的含义是什么）**、**V（Value，需要时能被取用的信息）**。模型用当前 token 的 Q 和所有 token 的 K 做点积得到注意力分数，Softmax 后变成权重，决定每个 V 贡献多少。**缓存缓的就是 K 和 V。**

---

## 二、匹配规则（最容易踩的坑）

> ⚠️ **必须从第 0 个 token 开始完全相同。**

- 中间某段重复 → **不算命中**
- 开头换一句话、多一个空格、JSON key 顺序变了、工具定义改了一个字 → **全部未命中**
- 要求是**逐字节（byte-for-byte）一致**

| 场景 | 结果 |
|:--|:--|
| 固定 3000 字角色设定 + 5000 字产品手册放最前，只换末尾用户提问 | ✅ 命中（那 8000 字不用重算） |
| 开头改了任意一个字 | ❌ 未命中，全部重算 |
| 多轮对话，下一轮带着上一轮的完整历史 | ✅ 命中上一轮生成的缓存 |

**生活化例子**：企业 AI 客服每次调用都固定携带 3000 字角色设定 + 5000 字产品手册（放最前面）。第一次提问完整计算 8000 字并存入缓存；第二、三次只换末尾的用户问题 → 前 8000 字命中缓存，不用重读手册，只算几十字。

## 四、术语速查

| 术语 | 含义 |
|:--|:--|
| **Cache Hit（缓存命中）** | 本次输入的前缀之前已完整计算并存于缓存，直接复用 |
| **Cache Miss（缓存未命中）** | 前缀无缓存，全部文字完整重算，耗时、计费更高 |
| **缓存命中率** | 一次调用中：命中缓存的 token ÷ 总输入 token。越高 = 重复计算越少 |
| **KV Cache** | 大模型推理的核心缓存，存注意力计算的 K/V 向量。**前缀缓存本质就是复用 KV Cache** |
| **Prefix Cache（前缀缓存）** | 按"从第 0 个 token 开始的前缀"做匹配的缓存机制 |
| **TTFT** | Time To First Token，首字延迟——用户感知"快不快"的关键指标 |
| **Prefill / Decode** | 预填充（读输入，最贵）/ 生成（逐字输出） |

## 五、各厂商实现差异（重要：不能混为一谈）

| 厂商 | 启用方式 | 最小粒度 | 保留时间 | 备注 |
|:--|:--|:--|:--|:--|
| **OpenAI** | **自动**（≥1024 token 起） | 128 token 步长 | 内存缓存约 5-10 分钟，尖峰可达 1 小时；扩展缓存可到 **24 小时** | 可用 `prompt_cache_key` 优化路由，`prompt_cache_retention` 控制保留 |
| **Anthropic Claude** | **需显式标记** `cache_control`（通常 `ephemeral`） | 按标记的内容块 | 约 5 分钟 | 不标记就不缓存 |
| **DeepSeek** | **自动**，无需改代码 | **64 token**（小于 64 不缓存） | 不用后自动清理，通常**几小时到几天** | 磁盘级缓存；**不保证 100% 命中**（best-effort） |
| **Google Gemini** | 隐式 + 显式缓存对象 | — | 可配置 TTL | 两种模式并存 |

**安全说明**：DeepSeek 官方说明每个用户的缓存**相互隔离、逻辑上不可见**，未使用的缓存条目会自动清除，不会被留存或挪作他用。

## 六、实用结论：怎么让缓存更容易命中

**唯一核心原则**：

> **静态内容放最前面，动态内容放最后。**

具体做法：
1. **提示词结构化**——固定的系统指令、角色设定、知识库全文、工具定义、Few-shot 示例 → 全部前置
2. **变化的部分后置**——用户当前问题、检索到的片段、临时元数据 → 放结尾
3. **保持逐字节一致**——不要随意调整 JSON key 顺序、不要在固定段落里加空格
4. **监控指标**——OpenAI 看 `usage.prompt_tokens_details.cached_tokens`；DeepSeek 看 `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens`
5. **警惕上下文压缩**——压缩、改写历史会破坏前缀一致性，可能把命中率打回原点

**反过来解释一个常见现象**：为什么有些对话越聊越快、有些突然变慢？

- **变快**：每轮都是"系统提示词 + 完整历史 + 新问题"，历史是**追加**的，前缀一直没变 → 持续命中
- **突然变慢**：中途改了系统提示词、切换了模型、或工具定义变了 → 前缀变了 → 全量重算

## 七、落地对接：这对你的实际工作意味着什么

| 场景 | 具体做法 |
|:--|:--|
| **反复用豆包/WorkBuddy 处理同一份长材料**（如志愿者排班规则、采购制度全文） | 把长材料放在对话最前面固定下来，只在末尾换问题 → 后续轮次明显变快 |
| **长文档反复追问**（如一份 50 页招标文件逐条核对） | 先一次性把全文喂进去，之后所有追问都在同一会话内进行，别开新会话重来 |
| **开发中调用大模型 API**（如「天使之翼」未来接入 AI 功能） | 固定前缀（系统提示 + 少样本示例）前置；成本敏感的长文批处理**挪到空闲时段跑，费用直接减半** |
| **知识库 RAG 场景** | 把固定的系统提示 + 常用背景资料做成稳定前缀；检索到的动态片段放最后 |
| **本地部署（自建推理）** | 同样适用 KV Cache 逻辑——理解为"省掉重复 Prefill"即可，与厂商是云是本地无关 |

**一个直接的省钱判断**：如果你有一个每天要跑几十次的长提示词任务，把它改造成"固定前缀 + 尾部变量"，成本可能从 ¥1/百万降到 ¥0.02/百万——**50 倍差距**，挪到空闲时段再减半。
